1. Vision y limites del producto
Servinex debe operar como una empresa de servicios tecnicos con una capa tecnologica interna. La plataforma 
no pretende convertir el negocio en un marketplace publico ni obligar al cliente a registrarse. Su funcion es 
controlar la operacion, estandarizar al proveedor, reducir la exposicion de datos del cliente y dejar evidencia 
trazable de cada servicio.
1.1 Objetivos del MVP
 Capturar internamente cada solicitud recibida por WhatsApp, llamada o publicidad.
 Crear una orden de servicio con folio unico y datos comerciales separados de los datos que ve el proveedor.
 Asignar un proveedor y generar una liga privada del servicio.
 Generar automaticamente un mensaje listo para copiar y enviar manualmente por WhatsApp.
 Permitir que el proveedor acepte o rechace con el minimo numero de pasos.
 Permitir que el proveedor marque avance y entregue un reporte con evidencia fotografica.
 Permitir que OPS revise, cierre el servicio y registre el pago al proveedor.
 Mantener auditoria de cambios y minimizar la fuga de datos/clientes.
1.2 Fuera de alcance del MVP
 Portal, cuenta o aplicacion para el cliente final.
 WhatsApp Cloud API, bots, automatizaciones oficiales de Meta o chatbot.
 Cobro en linea al cliente dentro de la plataforma.
 GPS en tiempo real del proveedor.
 App nativa iOS/Android.
 Marketplace publico donde los proveedores compiten por clientes.
 Facturacion fiscal automatica o integracion contable.
 IA para diagnostico o asignacion automatica en la primera version.
PRINCIPIO DE PRODUCTO
El proveedor debe poder completar todo desde el navegador de su telefono. No debe instalar nada, crear 
una contrasena ni aprender un sistema complejo para el MVP.
2. Arquitectura general
La aplicacion web se publica en Vercel. Toda regla de negocio sensible pasa por una API propia desplegada en Railway. 
Supabase funciona como base de datos PostgreSQL, autenticacion del personal interno y almacenamiento privado de evidencias. 
El proveedor accede al mismo frontend mediante una ruta especial que recibe un token de asignacion.

REGLA TECNICA
La SUPABASE_SERVICE_ROLE_KEY nunca debe existir en el frontend ni en Vercel como variable publica. 
Solo Railway puede usarla. El navegador trabaja contra la API de Servinex y, para archivos, con URLs 
firmadas temporales.
3.1 Por que Railway si Supabase ya tiene backend
Railway se conserva como capa de negocio porque el flujo necesita reglas que no deben quedar dispersas en el 
navegador: generacion y revocacion de tokens, ocultamiento de campos, cambios de estado permitidos, calculos 
de margen, auditoria, validaciones y permisos. Supabase queda como infraestructura de datos, no como 
sustituto de la API de negocio.

5. Flujo operativo end-to-end
1. Captura: El cliente escribe o llama. OPS registra manualmente nombre, telefono, zona, direccion, tipo de 
servicio, descripcion, fecha y precio al cliente.

2. Asignacion: OPS selecciona al proveedor. En el inicio habra uno, pero el modelo debe permitir varios sin 
rediseñar la base.
3. Oferta: El sistema registra el pago ofrecido al proveedor, genera token seguro, liga privada y mensaje de 
WhatsApp.
4. Aceptacion: El proveedor abre la liga y ve un resumen minimo: folio, servicio, zona, horario y pago. Acepta o 
rechaza.
5. Ejecucion: Al aceptar, se habilitan los datos operativos necesarios. El proveedor puede marcar En camino y 
En sitio/Iniciar servicio.
6. Reporte: El proveedor carga fotos de antes y despues, trabajo realizado y materiales/observaciones. Envia el 
reporte.
7. Revision: OPS revisa evidencia. Si cumple, cierra el servicio y habilita/registre el pago al proveedor.
8. Archivo: La liga del proveedor se revoca al cerrar/cancelar. Evidencia y auditoria quedan disponibles 
internamente.

7. Partner Link - experiencia del proveedor
META DE UX
Un proveedor que nunca ha usado la plataforma debe entenderla sin capacitacion. Botones grandes, una 
accion principal por pantalla y cero menus complejos.
7.1 Acceso sin cuenta en el MVP
El proveedor recibe una liga como https://app.servinex.mx/p/<TOKEN>. No inicia sesion. El token identifica 
exclusivamente la asignacion y sirve como credencial temporal. La API valida el hash del token, expiracion, 
estado y revocacion antes de devolver cualquier dato.

7.3 Formulario de reporte obligatorio
 Foto(s) antes: minimo 1, maximo recomendado 5.
 Trabajo realizado: obligatorio, 10 a 1,000 caracteres.
 Materiales utilizados: opcional en MVP; campo libre.

 Checkbox: "Confirmo que la evidencia corresponde al servicio realizado".

NO PEDIR AL PROVEEDOR
No solicitar datos que OPS ya conoce: nombre del cliente, telefono, precio vendido, margen o datos 
administrativos. El reporte debe tomar menos de 2 minutos en condiciones normales.
8. WhatsApp sin API
No se integrara WhatsApp Cloud API. El sistema solo genera el texto y la liga. El envio lo realiza una persona 
desde WhatsApp o WhatsApp Web. Esto reduce complejidad, costos y riesgo durante la validacion del negocio.
8.1 Botones en OPS
 Copiar mensaje: copia al portapapeles el texto completo.
 Abrir WhatsApp: usa un deep link wa.me con telefono del proveedor y texto URL-encoded. No envia 
automaticamente.
 Regenerar liga: revoca el token anterior y crea uno nuevo; registrar evento de auditoria.

10.1 Reglas criticas
 Nunca permitir dos asignaciones activas aceptadas para el mismo servicio en el MVP.
 Si se reasigna, revocar inmediatamente el token anterior.
 El proveedor no puede editar un reporte despues de enviado; OPS puede devolverlo a correccion en una fase

12. Evidencias y almacenamiento
 Bucket privado: service-evidence. No public bucket.
 Path sugerido: service-evidence/<service_uuid>/<assignment_uuid>/<report_uuid>/<before|after>/<uuid>.webp.
 Frontend comprime imagen antes de subir: maximo objetivo 1600-2000 px en lado largo, calidad 0.75-0.85.
 Recodificar imagen en el navegador para reducir peso y eliminar metadatos EXIF innecesarios.
 Backend genera URL de carga firmada temporal. El proveedor no recibe claves de Supabase.
 Validar MIME permitido: image/jpeg, image/png, image/webp. Rechazar ejecutables y archivos arbitrarios.
 Limite sugerido: 8 MB por archivo antes de compresion; la UI debe advertir y comprimir.
 OPS obtiene URL de lectura firmada de corta duracion cuando abre la galeria.
12.1 Integridad de evidencia
La fecha valida del sistema debe ser la hora de recepcion del backend, no la fecha EXIF de la foto. Registrar 
service_event por cada envio de reporte. En el MVP no es necesario geolocalizar la foto.
13. Finanzas y pago a proveedor
El objetivo no es crear contabilidad completa, sino evitar perder control del margen y de lo que se debe a cada 
proveedor.
Campo Regla
Precio cliente Visible solo OPS; capturado al crear/editar servicio.
Pago proveedor Se define al asignar; visible al proveedor.
Costos adicionales Opcional; visible OPS.
Margen bruto customer_price - provider_payout - additional_costs; 
calcular en backend.
Estado pago PENDING, APPROVED, PAID, CANCELLED.
Referencia Texto opcional de transferencia/folio bancario.
CONTROL
Un reporte aprobado puede marcar el pago como APPROVED, pero el cambio a PAID siempre debe ser una 
accion explicita de OPS con fecha y referencia.
14. Seguridad y prevencion de fuga de clientes
La tecnologia no puede impedir que un proveedor que esta fisicamente con un cliente intercambie un telefono. 
El objetivo del sistema es reducir la exposicion innecesaria, crear trazabilidad y hacer que Servinex sea el 
centro de la relacion operativa.
14.1 Controles tecnicos obligatorios
 Tokens: generar al menos 32 bytes aleatorios criptograficamente seguros; enviar raw token solo en la URL y 
almacenar SHA-256 del token en DB.

 Expiracion: cada token debe tener expires_at y revoked_at.
 Revocacion: al rechazar, reasignar, cancelar o cerrar.
 Rate limit: aplicar limites a endpoints de partner por IP/token para evitar fuerza bruta.
 No enumeracion: nunca usar service_order.id secuencial ni provider_id en URL publica.
 Minimizacion: la API Partner construye una respuesta separada; no serializar la entidad completa y luego ocultar 
en React.
 RLS: tablas sin lectura anonima directa. El frontend no consulta datos sensibles con anon key.
 Buckets privados y URLs firmadas.
 Audit log para cambios de precio, payout, proveedor, cancelacion, cierre y pago.
 Logs backend sin imprimir tokens completos, telefono del cliente o service role key.
14.2 Controles operativos recomendados
 El telefono del cliente no se muestra al proveedor por defecto.
 El proveedor contacta a Servinex si existe problema de acceso o llegada.
 La direccion exacta se libera solo tras aceptar.
 Al cerrar, el Partner Link deja de mostrar datos operativos sensibles.
 Acuerdo con proveedores: confidencialidad, tratamiento de datos y reglas de no captacion/no elusion revisadas 
por asesoria juridica local.
 Beneficios por permanencia: flujo constante, historial, pagos claros y prioridad; reducir el incentivo a saltarse a 
Servinex.
15. UX/UI y pantallas
15.1 Principios
 OPS desktop-first, responsive para tablet; proveedor mobile-first.
 Una accion primaria por pantalla en Partner Link.
 No usar menus laterales complejos en proveedor.
 Colores de estado consistentes, pero nunca depender solo del color; siempre mostrar texto.
 Confirmaciones para acciones destructivas: cancelar, reasignar, regenerar liga, marcar pagado.
 Skeleton/loading claro y mensajes de error en lenguaje humano.
 Autosave no necesario en MVP; evitar formularios gigantes.

17.3 Pipeline
 PR -> lint + typecheck + tests.
 Merge a main -> deploy automatico de web y API.
 Migraciones Supabase versionadas; nunca editar schema manualmente en produccion sin migration.
 Staging recomendado antes de produccion si el presupuesto lo permite.
 Backups de Supabase segun plan; documentar restauracion.

18.2 Pruebas tecnicas minimas
 Unit tests: transiciones de estado, calculo de margen, token hashing/validation.
 Integration tests API: accept/reject/report/revoke y permisos OPS.
 E2E: flujo completo desde crear servicio hasta cerrar.
 Test mobile: Chrome Android y Safari iPhone para Partner Link.
 Test de fotos desde camara real de telefono.
 Test de expiracion/revocacion de token.
 Test de acceso directo a Supabase anon: debe fallar para tablas sensibles.
 Test de carga duplicada y doble click: endpoints idempotentes donde aplique.
18.3 Definition of Done
 Funciona en produccion con HTTPS y dominios configurados.
 No existen secretos en bundle frontend ni repositorio.
 Migraciones y seed documentados.
 Logs de error disponibles en Railway.
 Manual corto para OPS: crear, asignar, copiar WhatsApp, revisar y cerrar.
 No hay errores de consola en flujo principal.
 Proveedor completa un servicio desde telefono sin ayuda tecnica.
 Backups/configuracion de Supabase revisados.
 Entrega de credenciales, repositorio y README al propietario de Servinex.

NO SOBRECONSTRUIR
Durante el MVP no crear chat interno, mapas avanzados, marketplace, rankings, IA, app nativa ni 
automatizacion de WhatsApp. Validar primero que Servinex puede generar, asignar, ejecutar y cerrar 
servicios con disciplina.
20. Fase 2 / escalabilidad
 Cuenta persistente de proveedor con historial, pagos y metricas.
 OTP por SMS o autenticacion mas fuerte para Partner Portal.
 Asignacion recomendada por zona, especialidad, score y disponibilidad.
 Catalogo de tarifas por servicio y proveedor.
 Garantias/retrabajos ligados al servicio original.
 Notificaciones push/PWA y recordatorios.
 Integracion oficial de WhatsApp cuando el volumen justifique costo y complejidad.
 Integracion de pagos/facturacion.
 Clientes empresariales internos con multiples sedes; sin necesidad de portal publico.
 Dashboard de cohortes: repeticion, margen por categoria, tasa de aceptacion, SLA.

CRITERIO FINAL DE EXITO
El MVP esta bien hecho si una persona de OPS puede recibir un lead, crear y asignar un servicio, enviar 
manualmente una liga por WhatsApp, el proveedor puede aceptar y reportar desde su telefono, y OPS 
puede revisar, cerrar y controlar el pago sin exponer datos comerciales al proveedor.
